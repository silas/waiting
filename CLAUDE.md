# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

"Waiting" is a macOS menu bar app (SwiftUI `MenuBarExtra`; icon is the `MenuBarIcon` template SVG in `Mac/Assets.xcassets`). The app icon (Finder, Settings, update dialogs) is the Icon Composer file `Mac/AppIcon.icon`: the same glyph, white on `#0d1117` like the website's `logo.svg`. It has no Dock icon or main window (`LSUIElement = YES`). Bundle ID: `dev.waiting.mac`.

## Build & run

There is a single Xcode project `mac.xcodeproj` with two targets: `Mac` (the menu bar app, product `Waiting.app`) and `waiting` (a command-line tool). Building the `Mac` scheme also builds `waiting` and embeds it at `Waiting.app/Contents/Helpers/waiting`. It lives in `Helpers`, not `MacOS`, because on a case-insensitive filesystem it would collide with the app executable `Waiting`. There is no test target in the Xcode project; the unit and e2e tests are separate Swift packages (see Testing). The only Swift package dependency is Sparkle (`Mac` target only; `Package.resolved` is in `mac.xcodeproj/project.xcworkspace`).

```sh
# Build (output goes to ./build, which is gitignored)
xcodebuild -project mac.xcodeproj -scheme Mac -configuration Debug -derivedDataPath build build

# Run the built app (appears in the menu bar, not the Dock)
open build/Build/Products/Debug/Waiting.app

# Install the Claude Code or Codex hooks (points them at this build's CLI)
build/Build/Products/Debug/Waiting.app/Contents/Helpers/waiting setup claude
build/Build/Products/Debug/Waiting.app/Contents/Helpers/waiting setup codex

# Install the VS Code extension (needed for VS Code terminal focus)
build/Build/Products/Debug/Waiting.app/Contents/Helpers/waiting setup vscode

# Simulate a Claude Code hook event (the CLI reads hook JSON on stdin)
echo '{"session_id":"s1","hook_event_name":"Stop","cwd":"/tmp/demo"}' \
  | build/Build/Products/Debug/Waiting.app/Contents/Helpers/waiting hook claude
```

## Testing

`UnitTests/` is a Swift package (swift-testing) for logic the e2e tests can't easily stage from outside, such as process tables and config files. `make test` runs it; it doesn't need an app build. Its `WaitingCore` target is made of symlinks into the app's sources (`Shared/`, `CLI/CodexClient.swift` and `Mac/Session.swift`), compiled with the Xcode project's concurrency settings, so to test another file, link it into `UnitTests/Sources/WaitingCore`. Code there is tested with `@testable import WaitingCore`; logic that reads the system (processes, files) is split into a gatherer and a pure function that tests call with made-up input, as in `CodexClient.choose`, `AgentHooks.areCodexHooksTrusted` and `Session.next` (which takes the focus checks as closures).

`E2E/` is a Swift package (swift-testing) that tests the built `Waiting.app` and its CLI from the outside. `make e2e` builds, then runs the hook, setup and app tests; `make e2e-live` runs real `claude -p` and `codex exec` sessions, which use the user's sign-in and spend tokens. Both need `CONFIG=Debug`, and `AGENT=claude` (or `codex`) runs one harness's tests (`WAITING_E2E_AGENTS`). Tests run in parallel, so subprocess I/O goes through files, not pipes (other tests' children would hold a pipe open).

- Isolation: the CLI posts to `WAITING_NOTIFICATION_NAME` when set, and each test uses its own name, so the user's running Waiting sees nothing. A Debug app launched with `WAITING_E2E_DIR` runs in test mode (`Mac/TestMode.swift`, compiled out of Release): it listens on `WAITING_NOTIFICATION_NAME`, keeps `sessions.json` in that directory, prunes every 1s, shows no icon, onboarding or alerts, registers no shortcuts, runs no AppleScript, doesn't start Sparkle, and after every change writes `state.json` (sessions in menu order, `waitingCount`, and the sessions `onStartWaiting` fired for). `make reset` and the user's settings are untouched, but it reads the same UserDefaults.
- `Sources/Listener` prints the events posted under a name (distributed notifications need a run loop, which the test runner lacks). The tests decode them with their own copies of the wire format (`Support/Wire.swift`), so a format change fails them. To check that something posts nothing, they run it and then a sentinel hook, and expect the sentinel's event next.
- Harnesses: each one is a `Harness` (`E2E/Tests/WaitingE2E/Harness.swift`) in `Harnesses/`. It provides the native hook input for each harness-neutral `Moment`, its config variable, hooks file and events for `waiting setup`, and how to run it non-interactively for the live tests, with hooks from `waiting setup` and without the user's own hooks (Claude: `--settings` with `--setting-sources project`; Codex: a scratch `CODEX_HOME` with a link to `auth.json`, and `--dangerously-bypass-hook-trust`). The shared suites (`HarnessContractTests`, `SetupTests`, the hook-to-app test in `AppTests`, `LiveTests`) run against every harness in `Harnesses.registered`. Rules only one harness has go in its own `<Agent>ContractTests`. To test a new harness, add a `Harness` and register it.

## Agent hooks → app

- The CLI dispatches commands in `CLI/main.swift`. `waiting hook claude` and `waiting hook codex` (`CLI/Hook.swift`) are meant to be run as Claude Code and Codex hook commands. Other harnesses will get their own `waiting hook <agent>` subcommands. Each one maps its harness's native input to a harness-neutral `AgentEvent` (`Shared/AgentEvent.swift`) and posts it as a `DistributedNotificationCenter` notification (`dev.waiting.mac.agent-event`). The app never sees harness-specific event names.
- `waiting setup <agent>` (`CLI/AgentSetup.swift`) and the Agents section of Settings' Integrations tab (`Mac/AgentHooksStatus.swift`, one row per detected agent) share `AgentHooks` (`Shared/AgentHooks.swift`), which detects and installs a `<waiting CLI path> hook <agent>` command hook for each event in the agent's `events`. Claude Code and Codex use the same JSON hooks format, so each agent is just a configuration: `AgentHooks.claude` (`Shared/ClaudeHooks.swift`) writes to `$CLAUDE_CONFIG_DIR/settings.json`, falling back to `~/.claude/settings.json`; `AgentHooks.codex` (`Shared/CodexHooks.swift`) writes to `$CODEX_HOME/hooks.json`, falling back to `~/.codex/hooks.json`. The CLI path is from `WaitingCLI` (`Shared/WaitingCLI.swift`): the CLI's own executable, or the app's embedded `Contents/Helpers/waiting`. To add an agent with the same format, add an `AgentHooks` configuration and add it to `AgentHooksStatus.all`.
  - The app doesn't inherit variables from the user's shell profile, so when its own environment has no `CLAUDE_CONFIG_DIR` (or `CODEX_HOME`) it takes it from the newest running process of that agent that has a tty (matched by `argv[0]`, since Claude's native binary's process name is its version), which runs none of the user's code. Processes without a tty (IDE extensions, Claude's desktop app, Codex's app server) are skipped, since they weren't started from the user's shell profile. With none running, it asks their interactive login shell (`Shared/LoginShell.swift`; after 5s, or once it has the value, the shell's whole process group is killed). The shell is spawned with responsibility disclaimed (`responsibility_spawnattrs_setdisclaim`), so privacy prompts its profile triggers aren't shown on Waiting's behalf. An answer is kept for the rest of the launch. If the shell fails, it uses the default directory but retries after 30s, and the Agents section says so and suggests `waiting setup <agent>` from a terminal. The CLI just uses its own environment.
  - It refuses to install while the CLI is on a read-only volume (`WaitingCLI.isTemporaryLocation`): a mounted DMG or App Translocation, whose paths go away. Settings shows a note to move the app to Applications in place of the Install button.
  - It replaces any existing hook that runs a copy of `waiting` for that agent, so rerunning it after moving the app just updates the path. Other hooks are left alone. Settings shows such hooks as Outdated, with an Update button; the app never changes them on its own.
  - An agent counts as detected when its config directory exists. With no agent detected, the Agents section says so.
  - Codex runs only hooks the user has trusted in its `/hooks` view, which records a `trusted_hash` in `config.toml` under `[hooks.state."<hooks.json path>:<snake_case event>:<group index>:<handler index>"]`. Waiting doesn't write these: until every installed hook has one (and isn't turned off with `enabled = false`), Settings shows Not trusted and says to use `/hooks`, and `waiting setup codex` says so too. The hash covers the command, so after an Update Codex wants it trusted again, but Waiting only checks that some hash is there. Keys are matched by the hooks file's real path (`realpath`), so a symlinked or differently written `CODEX_HOME` still matches. Settings rereads the status when the app becomes active.
  - It writes `settings.json.bak` first, and writes nothing if the hooks are already installed.
  - It rewrites the file with `JSONSerialization`, so keys end up sorted.
- `AgentEvent` carries a `SessionState`, generic fields (`cwd`, `title`, `message`, `terminal`), and a per-harness field for extras (`claude: ClaudeDetails`, `codex: CodexDetails`). Keep harness-specific data in that field.
- The Claude mapping lives in `CLI/Claude.swift`:
  - Events with an `agent_id` come from a subagent (with its parent's `session_id`) and are dropped, except needs-input `Notification`s (a subagent's permission prompt still needs the user).
  - `Stop` while `background_tasks` has a running subagent → working: subagents run in the background, so the turn ends while they work, and the agent continues on its own (with a `UserPromptSubmit`) when they finish. Other background tasks (shells) don't count, since they may never finish.
  - `Stop` → needs input
  - `StopFailure` (sent in place of `Stop` when the turn ends on an API error) → needs input, with a label for its `error` (Rate limited, Authentication failed, …; else `last_assistant_message`) as the message
  - `PermissionRequest` isn't used, though it comes ~6s before `permission_prompt`: it also fires for calls that are auto-denied without asking anyone (`dontAsk` mode, subagents that can't prompt), which would alert falsely. False alerts are worse than late ones.
  - `PreToolUse` for `AskUserQuestion` (the first question as the message) and `ExitPlanMode` → needs input: they wait for the user, and in `bypassPermissions` mode no notification follows
  - `Notification` is decided by `notification_type`. `permission_prompt`, `elicitation_dialog`, `elicitation_url_dialog`, `quota_auto_resume_stale`, `quota_auto_resume_disabled` and no type (older versions) → needs input. `elicitation_complete`, `elicitation_response` and `quota_auto_resume_fired` (the agent is back at work) → working. The rest are dropped: `idle_prompt` (the reminder sent about 60s after `Stop`) so it doesn't re-badge a session the user has already seen, `agent_needs_input`/`agent_completed` (the agent view relaying a background session's state, which that session sends itself) so the agent view's session isn't badged too, `auth_success`, and unknown types.
  - Other `UserPromptSubmit`/`PreToolUse`/`PostToolUse` → working
  - An Esc interrupt sends no hook, so the session stays working until its next event.
  - `SessionStart` → idle, except with `source` `compact`, which is dropped because auto-compaction can happen mid-turn
  - `PreCompact` with `trigger` `manual` (the user ran `/compact`) → idle; auto compaction is dropped
  - `SessionEnd` → ended (the app removes the session)
  - Anything else is dropped and never posted.
  - `cwd` is `CLAUDE_PROJECT_DIR` from the hook's environment, falling back to the input's `cwd`, which follows the Bash tool's `cd` and would rename the session.
  - For needs-input events, `Stop`, `UserPromptSubmit` and `SessionStart` (not the frequent tool hooks), `title` is read from the last 1 MB of `transcript_path` (`CLI/ClaudeTranscript.swift`): the latest `custom-title` entry (`/rename`), else the latest `ai-title` (generated; Claude Code re-appends these as the session goes on). These entries are undocumented, so a missing title just leaves the session's previous one.
  - Background sessions (`claude --bg`, or ← in a session) run in a `claude daemon`, each on a pty no terminal shows, with `CLAUDE_CODE_SESSION_KIND=bg` in the agent process's environment (`Shared/ClaudeAttach.swift`; hooks don't get it). Their inherited tty and environment are stale, so the terminal sent is that of the newest `claude attach <job ID>` process with a tty (job ID: `CLAUDE_JOB_DIR`'s last component, else the session ID's first 8 characters), else nil, which leaves the session's previous terminal. The agent view (←) shows a session in its own process, and nothing outside it (sockets, `~/.claude/daemon`) says which, so for `UserPromptSubmit` with no attach process it guesses: the terminal of the interactive, non-background Claude Code process whose tty was read from last (`ProcessTable.lastInput`), if that was in the last 3s. The process is the session's own, so unlike Codex's guesses this isn't marked as one. If the user then switches sessions in that agent view, Waiting still takes the tab as each one's it guessed, so while it's focused they're all marked seen. Like a Codex session that couldn't be told apart, one with no terminal yet is only marked seen when clicked. Tool hooks skip the search and send no terminal.
- The Codex mapping lives in `CLI/Codex.swift`:
  - Events with an `agent_id` come from a subagent (with its parent's `session_id`) and are dropped.
  - `Stop` → needs input; `PermissionRequest` (sent before an approval prompt) → needs input, with `tool_input.description` (else "Approve <tool>") as the message
  - `PreToolUse` for `request_user_input` (plan-mode questions, which don't go through `PermissionRequest`) → needs input, with the first question as the message
  - Other `UserPromptSubmit`/`PreToolUse`/`PostToolUse` → working
  - A turn that ends on an error (API, usage limit) sends no hook, so the session stays working until its next event.
  - `SessionStart` → idle, except with `source` `compact`, which is dropped; `Interrupt` (the user stopped the turn) and `PreCompact` with `trigger` `manual` → idle
  - `SessionEnd` → ended. Anything else is dropped.
  - For `Stop`, `PermissionRequest`, `request_user_input`, `UserPromptSubmit` and `SessionStart`, `title` is the session's latest `thread_name` in the last 1 MB of `$CODEX_HOME/session_index.jsonl` (`CLI/CodexSessionIndex.swift`), written by `/rename` and by Codex's generated titles.
  - The terminal UI usually runs sessions in a shared background app server (`codex app-server --managed-daemon`), so hooks are its children: their ancestors have no tty and their environment is the server's. When the nearest non-shell ancestor's arguments contain `app-server` and `--managed-daemon`, `CodexClient` (`CLI/CodexClient.swift`) finds the interactive `codex` process (has a tty, isn't `app-server`; for npm installs, the native child of the Node wrapper) whose arguments contain the session ID (`codex resume <id>`), else the only one whose working directory (`ProcessTable.currentDirectory`) is the session's cwd, and takes the terminal and process from it. When several share that cwd, `UserPromptSubmit` and `SessionStart` (the user just typed into the session's terminal UI: a prompt, launching, `/new`, `/resume`) take the one whose tty was read from last (its access time, `ProcessTable.lastInput`, as `w` uses for idle time), if that was in the last 3s. `Stop` and `PermissionRequest` don't, since the user may be typing into another one in that cwd just then. Even so it can be wrong (a prompt queued during a turn is submitted when the turn ends), so the event says it's a guess (`CodexDetails.locationIsGuess`): the app only uses a guessed terminal and process for a session that has neither, and never removes other sessions with that process. If there's none or it can't be told apart, both are nil, so the session keeps the ones it had. The server itself is never sent as the process. `PreToolUse` and `PostToolUse` (except for `request_user_input`) skip this search (both are nil), since it scans every process with a tty and the turn's `UserPromptSubmit` and `Stop` already do it. IDE extensions and the desktop app run their own app server without `--managed-daemon` and have no terminal UI, so there's no search (another session's terminal UI in the same cwd would be taken as theirs): the terminal is detected as usual and the process is nil. Without any server, the hook is the terminal UI's grandchild and detection works as for Claude.
- The payload is JSON in the notification's `object` string, because `userInfo` is dropped for sandboxed receivers.
- `Shared/` is compiled into both targets, so it holds the single definition of the wire format.
- `Mac/SessionStore.swift` keeps one `Session` per `"<agent>:<session_id>"`. Events older than the session's `lastUpdated` are ignored. Each hook is a separate CLI process, so events can arrive out of order: events sent before a session ended are also ignored for 60s after the end (`SessionStore.ended`), so they can't bring it back.
- `AgentEvent.process` identifies the agent's own process by PID and start time (`Shared/ProcessTable.swift`). The CLI takes it from the nearest ancestor that isn't a shell (`CLI/AgentProcessDetection.swift`). On launch and every 15s, the app drops sessions whose process has exited, which covers agents that crashed or were killed without sending an end event.
- State is saved on quit (`~/Library/Application Support/dev.waiting.mac/sessions.json`) and restored only if the app relaunches within 2 minutes, as after a Sparkle update. Otherwise it starts empty, since events sent while it wasn't running are lost. After a crash nothing is saved.
- A new session ID from the same agent process (`/clear`, `/resume`) replaces the old one, in case the old ID's end event was lost.

## Terminal focus

- The menu bar icon switches to `MenuBarIconAttention` when any session needs input (`SessionStore.waitingCount`). A needs-input session is marked seen (back to idle, until its next event) when its tab becomes focused, when an event arrives while its tab is already focused, or when it's clicked in the menu (`SessionStore.markFocusedSeen`, driven by `FocusMonitor.onChange`).
- The CLI captures where it runs as a `TerminalLocation` (`Shared/TerminalLocation.swift`, detection in `Shared/TerminalDetection.swift`, which the app also uses on tmux clients):
  - The bundle ID comes from `__CFBundleIdentifier`, then the `TERM_PROGRAM` table, then the first ancestor process that is an app.
  - The tty is the controlling terminal of the furthest ancestor process that has one: the terminal's own. `sudo` (with `use_pty`, as with `sudo --login`) and `script` run their command on a new pty that no terminal knows, so the nearest one wouldn't match any tab. Inside tmux the server has no tty, so it's still the pane's.
  - It also keeps an allowlist of terminal env vars.
  - It records raw identifiers and doesn't interpret them.
- `Mac/FocusMonitor.swift` watches the frontmost app. While that app has a `TerminalAdapter` (`Mac/Terminals/`), it polls `focusedTabKey()` once a second, because tab switches post no notification.
- All adapters use AppleScript. This triggers a one-time Automation permission prompt per terminal. If the permission is denied, no tab is ever considered focused.
  - iTerm2 and Terminal.app key tabs by tty.
  - VS Code and its forks (Insiders, Cursor, VSCodium) can't be scripted, so they need the companion extension instead (see below).
  - Ghostty (1.3+) keys terminals (panes) by their scripting `id`. It doesn't expose a tty or tell shells their ID, so the app learns it into `Session.learnedTabKey` (`TerminalAdapter.learnTabKey`). When a new session starts idle, or a session moves into working from another state, the user just typed in it, so if Ghostty is frontmost the focused terminal is the session's. Otherwise, on any event or when shown, it uses the only terminal whose `working directory` is the session's cwd, if exactly one matches. The learned key is stored with the terminal it was learned in (`Session.learnedTab`) and only used while that's still the terminal, so a changed `TerminalLocation`, or for tmux a client in a different terminal, means relearning.
- VS Code (`Mac/Terminals/VSCodeAdapter.swift`, one instance per editor, told apart by URL scheme) keys terminals by tty. The extension lives in `VSCode/` (plain JS, no build step):
  - Each window writes `~/Library/Application Support/dev.waiting.mac/vscode/<scheme>-<extension host pid>.json` with its focus state, its terminals' shell PIDs and the active one. The app maps shell PIDs to ttys with `ProcessTable.tty`, and deletes files whose extension host has exited.
  - The file also holds `showURI` from `vscode.env.asExternalUri`, which carries the window's `windowId`. Opening it with `pid=<shell pid>` added makes VS Code route it to that window's URI handler, which shows the terminal, and focus the window.
  - With no state files (extension missing or editor not running), `selectTab` returns `.failed`, so the editor is just activated.
  - The `Mac` target's "Package VS Code Extension" Run Script phase zips `VSCode/` into `Waiting.app/Contents/Resources/waiting.vsix`. When adding a file to the extension, add it to that phase's input paths and zip command. The install logic is in `Shared/VSCodeExtension.swift`. It installs the vsix with each installed editor's bundled CLI (`--install-extension`).
  - Users install it from the Editors section of Settings' Integrations tab (`Mac/VSCodeExtensionStatus.swift`), or with `waiting setup vscode` (`CLI/VSCodeSetup.swift`).
  - On launch, the app updates the extension in editors where an older version is installed (`VSCodeExtensionStatus.updateInstalled`). It never installs into an editor that doesn't already have it.
  - Updates are detected by version, so bump `version` in both `VSCode/extension/package.json` and `VSCode/extension.vsixmanifest` whenever the extension changes.
- tmux (`Mac/Terminals/Tmux.swift`) isn't a `TerminalAdapter` but a layer on top of them. Inside tmux, the CLI's tty is the pane's and its bundle ID is whatever terminal started the tmux server, so the app ignores those:
  - A session is identified by its pane (`TMUX` and `TMUX_PANE` from `TerminalLocation.environment`; the CLI doesn't change).
  - The outer terminal is resolved live from the tmux client best placed to show the pane: the client's environment is read with `ProcessTable.environment` (`KERN_PROCARGS2`) and run through `TerminalLocation.detect(pid:environment:)`, with the client's tty as the tab key. So detach and reattach elsewhere just works, under any adapter.
  - tmux is run as the server's own executable (`ProcessTable.executablePath` of the PID in `TMUX`), since the app's PATH may not include it. Each call has a 1s timeout because it runs on the main actor.
  - Showing a session runs `switch-client`/`select-window`/`select-pane` in that client, then selects the client's tab. A session whose pane or server is gone is removed. One whose pane can't be shown (no client attached, its terminal can't be detected, or tmux didn't answer) is kept, and the terminal that started the tmux server is activated if it's running.
  - `FocusMonitor` also records which panes are current in clients of the frontmost terminal (`Focus.tmuxViews`), so switching tmux windows counts as a focus change. It only queries servers that some session is in (`tmuxServers`).
  - For tmux sessions, `learnTabKey` only runs when the user is known to be there.
  - Nested tmux, tmux over SSH and Zellij aren't supported.
- Each menu item is the session's name (and status), with its title and, while it needs input, the agent's message as the item's subtitle. The menu lists needs-input sessions first, longest-waiting first, then the rest, most recent first (`SessionStore.sorted`). The first ten items get ⌘1…⌘9, ⌘0.
- Holding ⌥ turns each item into "Remove <name>" (with ⌥⌘1…⌥⌘0), using SwiftUI `modifierKeyAlternate`. "Clear Idle Sessions" removes every idle session.
- Clicking a session in the menu marks it seen and calls `TerminalAdapters.show`, which uses the adapter's `selectTab` to select the tab and raise its window, then activates the terminal app. Terminals without an adapter are just activated. If the tab or the terminal app is gone, the session is removed instead; for tmux sessions, only if the pane is gone. A session with no terminal info yet (a Codex session whose terminal UI couldn't be told apart) is only marked seen.
- To add a terminal: write a `TerminalAdapter` (`tabKey(for:)`, `focusedTabKey()`, `selectTab(_:)`, and `learnTabKey(for:userIsHere:)` if tabs can't be identified from what the CLI captures), register it in `TerminalAdapters.all`, and add any env var it needs to `TerminalLocation.environmentKeys`.
- Optional attention effects, all off by default, are toggled in the Alerts tab of Settings and persisted by `Mac/Attention/AttentionSettings.swift` (`attention.<name>` in UserDefaults):
  - The count shows the number of waiting sessions next to the plain icon, in place of the badge.
  - The pulse, the popup, the sound and the screen-edge glow play once, from `SessionStore.onStartWaiting`, when a session moves into needs-input and isn't in the focused tab. The pulse animates the status item button's layer (`MenuBarList.pulse`), because SwiftUI doesn't animate `MenuBarExtra` labels. The glow (`ScreenEdgeGlow`) is a click-through panel along the top of the screen the pointer is on. Its color is System Accent (amber when the accent is graphite), Amber, Purple or a custom sRGB color; Settings flashes a preview when it's turned on or recolored, live while a custom color is being picked, and likewise pulses the icon when the pulse is turned on and shows a sample count of 1 for 2s when the count is turned on with nothing waiting (`AttentionSettings.previewCount`).
  - The popup (`MenuBarPopup`) is a glass capsule under the menu bar icon, as wide as its text (up to 280pt), like the one macOS shows when headphones connect, with the session's name and its title (else its message, else "Needs input"), and the agent's logo (`ClaudeIcon` and `CodexIcon` in the asset catalog, from Simple Icons; `CodexIcon` is a template image, so it takes the text color) or the app icon for agents without one. It plays from `onStartWaiting` like the others, stays 4s (longer while the pointer is over it), and clicking it shows the session. It's a non-activating panel positioned from `MenuBarList.statusButtonFrame`, falling back to the right end of the menu bar when the icon isn't on screen. Settings shows a sample when it's turned on.
  - The sound is a system alert sound from `/System/Library/Sounds` (default Glass), played with `NSSound(named:)`. Settings plays it when it's turned on or a different sound is picked.

## Global shortcuts & settings

- The menu has a "Settings…" item that opens the SwiftUI `Settings` scene (`Mac/SettingsView.swift`), which has General (start at login, global shortcuts, updates), Alerts and Integrations (Agents: Claude Code and Codex hooks; Editors: VS Code extension, hidden when no editor is installed) tabs. The app has no Dock icon, so it calls `NSApp.activate()` first, or the window would open behind the frontmost app.
- "Start at login" (`Mac/LaunchAtLogin.swift`) registers the app with `SMAppService.mainApp`. The system owns that state (users can change it in System Settings > Login Items), so it's reread when the app becomes active instead of being stored. It's on by default: Release builds register once on first launch (`launchAtLogin.registeredByDefault` in UserDefaults), so turning it off sticks; a launch from a disk image or App Translocation (`WaitingCLI.isTemporaryLocation`) doesn't count. Debug builds skip this.
- On first launch, an onboarding guide (`Mac/Onboarding.swift`) walks through agent setup (the Integrations tab's Agents and Editors sections, plus a note about the Automation prompt) then the Alerts section, then the General tab's sections. It reuses those Settings sections, so they're internal rather than private. It's a floating (`.windowLevel(.floating)`, always on top) SwiftUI `Window` scene that presents itself at launch via `defaultLaunchBehavior` (calling `openWindow` from the menu bar label's `onAppear` is too early and doesn't reliably open it); an AppKit `NSHostingController` window with `.preferredContentSize` sizing crashed in a constraint-update loop with the self-sizing `Form`. Opening the app while it's running would make SwiftUI reopen it, as the first window scene, even after it's been completed, so `AppDelegate` (in `Mac/WaitingApp.swift`) returns false from `applicationShouldHandleReopen` and opens the menu instead. It sets `onboarding.completed` in UserDefaults as soon as it appears (not on close, because quitting the app also runs `onDisappear`), so it's shown once. While it's open, AppleScript is paused (`AppleScriptRunner.isPaused`, set in `WaitingApp.init`): scripts fail as if Automation were denied, so the Automation prompt can't appear over it. `SessionStore.show` and `showNext` (a menu click or the shortcut) run inside `AppleScriptRunner.userInitiated`, which still runs them; anything else that shows a session must too, or a paused `selectTab` makes the session look gone. To see it again, run `make reset run` (which also resets every other setting and the Automation permissions) or `defaults delete ~/Library/Preferences/dev.waiting.mac.plist onboarding.completed` (by path: a stale `~/Library/Containers/dev.waiting.mac` makes `defaults` read the container's preferences instead).
- Global shortcuts live in `Mac/Shortcuts/`:
  - `HotKeys` wraps Carbon `RegisterEventHotKey`, which needs no permissions.
  - `ShortcutAction` lists the bindable actions with their titles and defaults.
  - `ShortcutSettings` persists bindings to UserDefaults (`shortcut.<action>`; a missing key means the default, JSON `null` means cleared) and keeps them registered. It records which actions failed to register (`unavailable`) and suspends all hot keys while one is being recorded.
  - `ShortcutRecorder` captures the next keyDown with a local `NSEvent` monitor. Esc cancels. A shortcut must include ⌃, ⌥ or ⌘ unless it's a function key.
- The actions are performed in `WaitingApp.init`:
  - "Jump to waiting or next session" (default ⌃⌥⌘L) calls `SessionStore.showNext`, which picks with `Session.next` (`Mac/Session.swift`, where `Session` and the menu order, `Session.menuOrder`, also live).
    - If any session needs input, it shows the longest-waiting one, which is the top of `sorted`.
    - Otherwise it cycles in menu order: it shows the next session after the one in the focused tab that's in a different tab (wrapping around). If no tab can be identified (no adapter, or Automation denied), it continues from the last session it showed while that session's terminal is frontmost; otherwise it shows the first session. Sessions with no terminal info yet are skipped, since showing them does nothing and they'd never count as current.
    - A session whose tab is gone is removed and the next one is tried.
  - "Open menu" (default ⌃⇧⌘L) calls `MenuBarList.open`. SwiftUI can't open a `MenuBarExtra`, so this clicks the `NSStatusBarButton` in the app's `NSStatusBarWindow`. It first waits (up to 2s) for ⌥ to be released, since holding ⌥ shows the menu's alternate Remove items.
- To add an action: add a case to `ShortcutAction` and handle it in `WaitingApp.init`.

## Project structure & settings

- App sources live in `Mac/`, CLI sources in `CLI/`, and code compiled into both in `Shared/`. All are file-system-synchronized groups: new files are picked up automatically, so there's no need to edit `project.pbxproj` to add sources.
- Most Info.plist values are set via `INFOPLIST_KEY_*` build settings in `project.pbxproj`. Keys Xcode doesn't know (Sparkle's `SU*`) go in `Mac/Info.plist`, which is merged into the generated one and excluded from the `Mac` group's resources by an exception set.
- Entry point is `Mac/WaitingApp.swift` (`@main struct WaitingApp`).
- Build settings worth knowing:
  - Deployment target is macOS 27.0.
  - The App Sandbox is disabled (it would block the AppleScript focus queries). Hardened Runtime is on for both targets (required for notarization); the app's `Mac/Waiting.entitlements` has `com.apple.security.automation.apple-events`.
  - `NSAppleEventsUsageDescription` is set via `INFOPLIST_KEY_NSAppleEventsUsageDescription`.
  - Swift 5 language mode with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` and approachable concurrency. Code is MainActor-isolated by default, so mark background work `nonisolated` or `@concurrent` explicitly.

## Updates & releases

- Sparkle 2 is wrapped by `Mac/Updater.swift` (`SPUStandardUpdaterController`). The menu has "Check for Updates…" and the General tab of Settings has an "Updates" section (automatic checks toggle, version, Check Now). It opts into gentle scheduled update reminders since the app has no Dock icon.
- `Mac/Info.plist` holds `SUFeedURL` (`https://releases.waiting.dev/appcast.xml`), `SUPublicEDKey` and `SUEnableAutomaticChecks`. The EdDSA private key lives in the release machine's login Keychain (created with Sparkle's `generate_keys`).
- Sparkle replaces the bundle in place, so the CLI path in the agents' hooks files stays valid across updates.
- `scripts/release.sh` archives, exports with Developer ID (`scripts/ExportOptions.plist`), notarizes (`NOTARY_PROFILE`, default `waiting-notary`), staples, zips into `UPDATES_DIR` and runs `generate_appcast` with delta updates off (`--maximum-deltas 0`; the zip is only a few MB). `UPDATES_DIR` must persist every past zip plus `appcast.xml`, which keeps the appcast's history. It also builds a signed, notarized `build/release/Waiting.dmg` for the website, kept out of `UPDATES_DIR` because `generate_appcast` would treat it as an update. `make upload` copies both to the R2 bucket behind `https://releases.waiting.dev/` with rclone (the DMG as the fixed `Waiting.dmg`, `appcast.xml` last).
- Bump `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` (both Mac configurations) for every release; Sparkle compares `CFBundleVersion`.
- Sparkle's tools are at `build/SourcePackages/artifacts/sparkle/Sparkle/bin/` after a build.
